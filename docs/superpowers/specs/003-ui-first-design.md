# 003 UI First Design

The rest of the 001 local prototype is re-sequenced so every planned page is built and clickable before the remaining API work starts. Pages run against a mock API in the browser that answers the contract in the 001 plan index, so switching to Flask later changes no page code.

## Goals

1. `npm run dev:mock` from `web/` opens a working app with no Flask or Postgres running
2. Every page slices 05 to 09 describe works in that mode: register, log in, search, artist, album, song, rating and review, playlists, history
3. A demo can run the full flow with realistic music, community ratings, loading states, and error messages
4. UI work may reshape the API contract, and the backend is built to the contract the finished pages use
5. Switching a page to the real API needs no change to that page, its hooks, or its tests

## Why

- Demo a realistic app early, before the API is finished
- Settle layouts and flows while they are cheap to change
- Frontend work proceeds without waiting on backend slices

## Decisions

| Topic | Decision | Reason |
|---|---|---|
| Data source | MSW (Mock Service Worker) intercepts `/api/*` in the browser | Pages keep the real client, hooks, and query keys, so integration is turning the mock off |
| Alternatives | Rejected sample data inside hooks and stubbed Flask routes | Two code paths in every hook, or backend work first, which defeats the goal |
| Scope | The pages slices 05 to 09 already plan, no new screens | Agreed scope |
| Contract | UI leads. A page needing a different route or shape updates the 001 index in the same PR, and the matching API task is revised before it runs | The finished screens decide the contract |
| Mode | `npm run dev:mock` runs `vite --mode mock`, plain `npm run dev` still proxies to Flask | One switch, no flag in page code |
| Build | Mock code loads through a dynamic import guarded by the mode, so `npm run build` never bundles it | The mock is dev tooling |
| Persistence | The mock store saves to `localStorage`, clearing site data resets it | A reload mid demo keeps the session and ratings |
| Latency | Every mock response waits 250 ms | Skeletons and button loading states are visible while building them |
| Seed data | Real artists, albums, and songs with their real MusicBrainz IDs, recorded once from MusicBrainz | Realistic demo, and IDs match what the API will cache |
| Unit tests | Page and hook tests keep `mockFetch` | No test churn, MSW is for running the app |
| Lifetime | Slice 10 deletes the mock, its dependency, and the script | Two implementations of the contract would drift |

## Phases

| Phase | Work | Plans |
|---|---|---|
| A0 Mock foundation | MSW setup, store, seed data, `dev:mock`, auth and catalog read handlers | new, 003 |
| A1 UI | 05 Tasks 2 to 4, 07 Task 3, 08 Tasks 3 and 4, 06 Tasks 3 to 5, 09 Task 2, each adding its feature's handlers | 001 slices, web tasks |
| B API | 05 Task 1, 06 Tasks 1 and 2, 07 Tasks 1 and 2, 08 Tasks 1 and 2, 09 Task 1 | 001 slices, API tasks |
| C Integration | 001 slice 10, plus removing the mock | 001 slice 10 |

A1 keeps the 001 dependency order between web tasks: 06 pages need the components from 07 Task 3 and 08 Task 3. B keeps the 001 order between API tasks: 05 Task 1 first, then 06, 07, 08, and 09 in parallel.

Before each B task runs, its plan is compared with the index and that feature's handler file. Any shape the UI changed is fixed in the plan first. After the endpoint merges, its pages are clicked through once with `npm run dev` against Flask.

## Architecture

```
web/
  package.json              msw dev dependency, "dev:mock": "vite --mode mock", msw.workerDirectory "public"
  public/mockServiceWorker.js   generated by msw init, inert unless the mock starts
  src/
    main.tsx                starts the worker before rendering when import.meta.env.MODE is "mock"
    mocks/
      browser.ts            setupWorker over every feature's handlers, 250 ms delay
      seed.ts               recorded catalog, users, ratings, playlists
      catalog.ts            static catalog lookups, summaries, search
      store.ts              persisted state, session, rating summaries
      respond.ts            route wrapper, errors, text and page helpers
      testing.ts            msw/node server and a fetch helper for handler tests
      handlers/
        auth.ts             A0
        catalog.ts          A0, search and detail routes
        ratings.ts          A1, slice 07
        playlists.ts        A1, slice 08
        history.ts          A1, slice 09
      *.test.ts             next to each module and handler file
```

Handlers split by feature like Flask blueprints, so a feature slice only touches its own handler file and its test. Shared reads such as rating summaries live in `store.ts`, while each feature's writes and validation live in its handler file. `browser.ts` composes the arrays once in A0, with empty arrays exported from the files A1 fills in.

Unhandled requests to `/api/*` log a warning naming the route, so a page calling a route no handler serves shows up at once instead of hanging.

## Store

The store and the handlers together follow the backend rules the UI displays:

- Ratings are half stars on the wire, stored as `score` 1 to 10
- Album and artist effective ratings follow the 001 spec: an explicit rating overrides, otherwise the rounded average of the user's song ratings for that album or artist, with `is_derived` and `song_count`
- Community averages round the mean of effective stars to one place, the same rule for every kind
- Text is trimmed and an empty result is stored as null, reviews max 2,000, playlist name max 100, description max 500, playlist max 500 songs
- Usernames are 3 to 30 of `[a-z0-9_]`, passwords at least 8 characters
- Search and review pages hold 25 and 20 items
- History lists explicit ratings only, newest first

Serializers build the exact JSON shapes the index defines, using the types from `src/api/types.ts`, so the compiler flags a mock that drifts from the contract.

State persists under one versioned `localStorage` key. A seed change bumps the version, which discards stale saved state.

## Seed data

- Four artists and five albums with full tracklists, about fifty songs: Radiohead's OK Computer and In Rainbows from the API fixtures, plus Portishead's Dummy, Björk's Homogenic, and Massive Attack's Mezzanine, all with real MusicBrainz IDs and titles recorded once during A0
- Three seed users with ratings and reviews spread across the catalog, so community averages and review lists are populated
- One demo account, its email and password listed in the README section for `dev:mock`
- One public playlist per seed user

An MBID outside the seed answers 404, since no live catalog sits behind the mock.

## Errors

Handlers answer with the contract error shape `{"error": {"code", "message"}}` and the API's messages:

| Case | Status | Code |
|---|---|---|
| Mutation while logged out | 401 | `unauthorized` |
| Invalid input | 422 | `validation_error` |
| Unknown MBID, playlist, or username | 404 | `not_found` |
| Username or email taken | 409 | `conflict` |

## Testing

- `store.test.ts` covers effective and community ratings including the override and its removal, persistence, and stale saved state
- Each handler file has a test that runs its handlers under `msw/node` and checks the contract responses, validation messages, and the error cases above
- Page and hook tests stay on `mockFetch` as the 001 plans write them
- `npm run build` is checked to contain no MSW code
